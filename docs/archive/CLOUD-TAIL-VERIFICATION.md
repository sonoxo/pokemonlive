# 云端尾帧 URL 接入验证

> 历史验收记录：内容对应记录时的版本，不作为当前运行说明；文内代码路径及命令以项目根目录为基准。

日期：2026-09-07（Asia/Shanghai）

本文记录云端尾帧首次接入时的验证。后续已删除上游 Range 下载/提帧及专用脚本，生产媒体配置改为 `extractTail: false`，播放与归档使用单次渐进 GET；云端 URL 共享与续段规则不变。当前传输验证见 `MEDIA-PIPELINE-VERIFICATION.md` 末尾。

## 改动范围

- 攻击视频由服务端直接调用 `fal-ai/ffmpeg-api/extract-frame`，明确指定 `frame_type: last`。
- 同一个原片 URL 的续段、归档及收尾/状态预热共享一次云端请求。末段也提帧，避免收尾等待一个永远不会创建的锚点。
- `FalVideoRunway` 接收到 HTTPS 图片 URL 后，直接传给下段 `image_url`；不下载该图、不经 storage.upload。种子、招式事实和播放切换逻辑未变。
- 生产 `VideoMediaCache` 配置 `extractRangeTail: false`，不启动本地 Range 提帧或本地整片提帧；即使误调用 `tail()` 也明确拒绝。播放/归档仍共享原有 Range-only 视频源，直接补齐缺口，不等提帧。
- 图片 URL 立即 resolve 连续性锚点，再异步写小型 URL 收据；原片下载完成后才下载 JPG 留作重启复用。磁盘、图片下载、媒体缓存满均不能清掉已经可用的云端 URL。
- 单请求有 60 秒截止，消费者取消不取消共享请求；云端失败不自动重发付费 POST，不重新购买视频，也不偷偷恢复本地 Range 提帧。缓存 30 分钟、最多 128 项，在途请求不可淘汰。
- 归档恢复优先 JPG，其次有效期内的 HTTPS URL，再其次从**已落盘原片**离线解码。在线 URL 到期或 runway 会话先被 TTL 清理，都能在重新核验计划与状态后读归档。
- 本地循环加工后的待机片和其它场景片保持现有实际尾帧提取，防止云端原片尾帧与加工后的播放画面不一致。旧 Range 提帧工具和测试保留用于诊断，不在生产攻击续段中运行。

## 自动化覆盖

`tests/cloud-tail-frame.test.js` 新增 9 项：

1. 单次 last POST、并发去重、独立取消、URL直达、指标不含密钥/媒体URL。
2. HTTP失败、非法输出、网络异常和超时只发一次POST；已取消/无效来源不提交；缓存容量及TTL有界。
3. 生产媒体配置只读播放/归档Range，两个本地提帧器均不调用，误调用tail明确失败。
4. 真实runway和归档组合：视频/图片尚未下载完时已提交下一段；每片只提一次，末段锚点也到达。
5. 图片/磁盘失败与视频缓存满不影响已交付锚点。
6. 云端失败停止后续提交，不重新生成已经完成的首片。
7. 提帧时取消演出立即退出，归档仍能取得共享结果且不购买下一片。
8. 重启优先JPG，新鲜URL可用，过期URL只读本地原片。
9. 两个真实锚点入口覆盖runway先过期、在线URL到期、场景不匹配以及未完成片拒绝。

初次受限环境基线：318/320通过；另外两项均因本地回环监听 `EPERM` 未能执行，不是断言失败。允许回环监听后，第一轮改动328/328通过；TTL审查修复后最终 **329/329通过**（`npm test`，约8.20秒）。`git diff --check`通过。

## 边界

每个新攻击视频会多一次云端提帧费用；未查询账户实际扣费。URL直传消除的是本地视频取尾与图片再上传依赖，不能消除fal排队/生成/图像拉取，以及浏览器视频下载、缓冲的耗时。此轮不保证完全无停顿。
