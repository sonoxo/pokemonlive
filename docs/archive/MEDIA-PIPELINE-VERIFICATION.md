## 已落地

- 同一攻击片的下载在归档、浏览器、后续分镜和状态锚点之间共享；尾帧只提取一次。完成归档后释放内存，服务重启后优先读取已归档尾帧 JPEG。
- 浏览器改用同源稳定地址。已知长度的普通 GET / `bytes=0-` 请求在服务端仍下载时就接收字节，不将“完整下载结束”变成首播前置条件；完成后支持本地文件 Range 和 HEAD。
- 有效尾帧提取完成即可交给依赖者，磁盘归档不阻塞下一个生成请求。归档失败不会抹掉已成功提取的真实尾帧。
- 场景视频区分可播放、尾帧可用和归档完成。完整可播放媒体写入后，客户端即可缓冲；待机闭环加工仍在发布前执行。下一段依赖尾帧时，仍等待真正提取完成，不传入空帧。
- 单个播放器断开或取消等待不会取消其他消费者共用的下载。下载有超时、大小和声明长度校验；归档中的缓存不会被 TTL / 容量回收误伤。
- 攻击片新增 `clip-N-media.json` 的 `downloadMs` / `tailFrameMs`；场景任务增加下载、循环加工、尾帧、可播放与归档耗时。

## 边界与后续实测

- 本轮改善重复传输、重复提帧及不必要的就绪等待，没有改变 fal 排队或模型推理速度。不能承诺后片始终在 5 秒内完成。
- 严格“上片尾帧→下片首帧”的生成仍需完整下载并提取上一段尾帧；浏览器渐进播放不解除该因果约束。
- 未知 Content-Length 或任意位置 Range 请求仍等待完整媒体；是否能很早解码也取决于 MP4 元数据位置及网络。
- 缓存每片上限 64MiB、最多 32 项、下载超时 45 秒；128MiB 是已完成可回收项的软预算，在途或归档固定项可暂时超过该预算。
- 待机视频必须完成闭环加工后才可发布；真实尾帧必须成功后才能用作下一次生成锚点。
- 没有进行真实 fal 网络环境下的修改前后 A/B 测量。下一次正常付费战斗可结合新增埋点比较下载、尾帧、浏览器缓冲和生成耗时，不将受控回放数据当作线上提速幅度。

## 2026-09-07：删除上游 Range

按用户要求删除上游 Range 分块下载、本地 Range 提帧及其专用诊断脚本与测试；不是只关闭开关。代码及历史诊断工具可从提交 `05de16f` 恢复。浏览器请求本地媒体的 Range / HEAD 仍保留，只消费同一个顺序下载缓存，不向 fal 再发 Range 请求。

攻击片使用 `VideoMediaCache({ extractTail: false })`，单次普通 GET，网络正文到达即交给播放器。归档仍等待完整文件和长度核验；两者共享一次请求。上游错误、206 部分响应、重定向及大小超限不会重复下载。客户端 `sharedDownloadOnly` 标记保留 45 秒等待上限及禁用 CDN 重复下载的约束。其他场景的回退策略不变。

云端尾帧 URL 的独立链路不变：续段/收尾/状态预热不等本地视频或 JPG 下载，末段仍提帧。已有缓存和战斗状态未修改。
