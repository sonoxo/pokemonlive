## 结论与门禁

换人演出结束到对手攻击的串行等待已消除于本轮样本：7,419 ms → 44 ms。
普通战斗分镜之间仍存在 2.77–3.74 秒尾帧停留，不能宣称完全无缝，也不能将代码审查通过当作零停顿验收通过。

保留三项改动：

1. 播放器优先复用服务端正在下载/归档的视频，避免浏览器再独立下载同一 CDN 文件。CDN 保留单次备用；三槽保帧和一次性伤害结算不变。
2. 主动换人：放出视频已就绪、真实尾帧可用时，即在训练家/收回/放出演出期间提交后续攻击。以新阵容的 sendout key 校验，播放顺序不变。正常完成才移交任务；跳过、重开、迟到 POST 有取消处理，不重复付费提交。
3. 新片间埋点：`clip_gap_ms`、`gap_generation_ms`、`gap_buffer_ms`、`gap_handoff_ms`。仅统计上一段结束之后的可见等待；handoff 包含真实首帧及异常回退恢复等待，不应解释为纯 CSS 切屏耗时。

## 普通分镜断点：最后一轮精确拆解

以下相对该轮选招时间：

| 事件 | 时刻 |
| --- | ---: |
| 第一段生成完成（浏览器观测） | 8.366s |
| 第一段开始播放 | 10.348s |
| 第一段结束 | 15.575s |
| 第二段生成完成（浏览器观测） | 16.922s |
| 第二段缓冲完成 | 19.310s |
| 第二段真实首帧 | 19.317s |

因此 3.742s 停留 = 1.347s 等待后段生成 + 2.388s 下载/解码缓冲 + 0.007s 起播切换。
下一段的生产链本身是：上段下载/尾帧 3.769s + 后段生成 4.908s，再加浏览器缓冲约 2.387s。仅压缩播放器切换毫秒数无法消除秒级等待。

原始逐段生成、下载与播放事件位于 `.local/live-perf-20260906/.local/runs/<会话>/clip-*.json`、`clip-*-media.json`、`playback.jsonl`。`network.jsonl` 可确认预提交确实发生于换人演出结束之前。换人后的 44ms 不包含已藏在换人演出中的生成时间，不能声称模型推理只需 44ms。

## 未保留的实验

- 三路并行 Range 下载：同一视频两组对照未获得稳定收益，有一组更慢；撤回。
- FFmpeg 远程 seek：正确尾帧，但多次网络往返约 5.19s；撤回。
- MP4 索引→最后 GOP Range：8 个真实视频的稀疏提取尾帧与全片 JPEG 逐字节一致；独立已缓存媒体读取约 2.93s，但最后两段真实并发运行均由完整下载先完成，`tailSource=full`，没有证明缩短片间等待。因此也从生产代码撤回，不留下额外网络请求。

## 剩余问题与下一步

1. **普通5秒分镜链仍未达零停顿目标。** 若继续严格使用上一段真实尾帧，则“尾帧到手→下一段生成→下载就绪”全部位于关键路径，必须小于剩余播放窗口。
2. 有效的新实验方向是将同一回合的双方动作编排为一条较长连续视频（例如10秒、内部多镜头），从结构上消除这处片间依赖；这会改变当前5秒分段策略，需要另行确认与新一轮生成测试额度。本轮没有擅自切换该方案。
3. 冷状态待机/听令、冷放出视频仍需单独实测；本轮缓存命中结果不能代表它们已经消除等待。
